## 1.React的`render(<App />);`

React 从设计上就把“内核”和“渲染器”分开了——组件、state、diff 这些核心逻辑完全不关心最终画到哪里，只负责生成一棵虚拟树并算出变化；画到哪是渲染器的事：

- **浏览器**：`react-dom` 把虚拟树转成真实的 DOM 节点（div/span），交给 CSS 布局，最后浏览器绘成像素
- **终端**：Ink 把同一棵虚拟树转成文本节点，用 yoga（和 React Native 同款的 flexbox 引擎）算布局，最后输出 ANSI 转义序列到 stdout

所以你会看到两边惊人地对称：`<Box flexDirection="row">` 约等于 CSS 的 `display: flex; flex-direction: row`；`render(<App/>)` 约等于 `createRoot(...).render(<App/>)`；状态变了都是走 reconciliation 只更新差异，而不是整屏重画。

真正的差别只有三点，都来自“介质”不同：

1. **输出介质**：浏览器是像素画布，终端是字符网格——所以没有圆角、没有字号，样式只剩颜色/加粗这些 ANSI 码能表达的东西
2. **事件来源**：浏览器是 DOM 事件（`onClick` 等），终端是 stdin 的按键流，所以这个项目用 `useInput` 而不是 `onClick`
3. **无持久实体**：DOM 节点是常驻、可查询的对象；终端只是一条被反复覆写的字符流，Ink 全屏重绘时靠 ANSI 光标控制只重写变化的行

理解了这一点，这个项目里所有 React 知识就都能复用了——你写 `useState`、props、组件拆分的方式和在网页里完全相同，唯一要换的脑子就是“我在往一个字符网格上排版”。



## 2.`?:`

1. `?:` 不是单独运算符，是“可选标记 `?` + 类型标注 `:`”。
2. `name?: string` 和 `name: string | undefined` 不完全一样：前者允许属性**不存在**；后者通常要求属性必须写出来，只是值可以是 `undefined`。读取可选属性时，类型通常也会被视为 `string | undefined`。



## 3.副作用函数

 ❯ （它只负责往 stdout 写，是个副作用函数）  这个副作用怎么理解？？

 ● 「副作用」（side effect）是函数式编程里的概念，意思是：一个函数除了「吃参数、吐返回值」之外，还碰了外部世界的东西。

>  对照着理解

   纯函数——==只依赖**输入**==，==只产出返回值，外界毫无变化==：

   ```ts
     const add = (a: number, b: number) => a + b;
     add(1, 2);  // 永远得 3。调不调它，世界都一样
   ```

   有副作用的函数——==干的事「漏」到了函数外面==：

   ```ts
     const frame = (...) => {
       stdout.write(...);    // 改变了终端屏幕 ← 副作用
       lastLines = ...;      // 改了外层变量     ← 副作用
     };
   ```

frame 的返回值是 undefined，等于「什么都没还给你」。调用它的全部意义就是那两个对外界的改变。所以说「它是个副作用函数」——你调用它不是为了拿结果，而是为了让事情发生。

  

> 常见的副作用类型

   • 往屏幕/文件/网络写东西（I/O）
   • 修改函数外部的变量（比如 frame 改 lastLines、needsClear）
   • 修改传进来的对象本身
   • console.log、弹窗、改数据库……

   为什么要区分这个概念

   副作用让函数的行为不再只由参数决定，变得更难预测、难测试：

   ```ts
     // 纯函数：看代码就知道结果，测起来直接断言返回值
     expect(add(1, 2)).toBe(3);

     // 副作用函数：结果写在屏幕上，想验证就得截获 stdout.write 的调用
     // （我们之前那个 .smoke.js 用 PassThrough 伪造 stdout，干的就是这件事）
   ```

   所以编程里有个常见原则：把副作用集中到少数地方，其余逻辑尽量保持「纯」。splash.ts 其实就是这个思路的缩影——frame 一个函数包揽了所有「往屏幕写」的脏活，外面的渐显/呼吸/淡出循环只管算颜色、做决策，逻辑就很干净。



### 3.*修改传进来的对象本身和console.log、弹窗、改数据库…… 为什么这两个也是副作用？

 ● 这两个都是「函数碰了不该碰的外部世界」，只是方向不同：一个是往回改，一个是往外漏。

   1. 「修改传进来的对象本身」为什么是副作用

   纯函数的定义：同样的输入，永远得到同样的输出，且对外界零影响。

   看一个反例：

   ```ts
 const user = { name: 'Yue', visits: 0 };

 function greet(u) {
   u.visits++;              // ← 修改了传进来的对象！
   return `你好 ${u.name}`;
 }

 greet(user);   // 返回值是 '你好 Yue'
 greet(user);   // 返回值还是 '你好 Yue'
   ```

   两次调用返回值一样，看起来挺"纯"？但 user 被偷偷改了：

   ```ts
     console.log(user.visits);  // 2 —— 外面的世界变了
   ```

   这就是副作用：函数的影响"漏"出了自身之外。调用方传参时以为只是借你用一下，结果你还回来的时候东西被改了——这在复杂系统里是 bug 的重灾区（比如两个函数共享同一个对象，A 改了，B 的行为悄悄变了）。

   ==🚀 对比一下纯的版本：==

   ```ts
     function greetPure(u) {
       return { ...u, visits: u.visits + 1 };  // 不碰原对象，造个新的还给你
     }
   ```

   原对象毫发无损，调用方拿到什么清清楚楚——这就是 React/Redux 那一套「不可变数据」哲学在终端 TUI 项目里同样适用的原因。

   2. 「console.log / 弹窗 / 改数据库」为什么是副作用

   这几个更直观——它们的共同点是：函数做了"改变外部世界"的事，而不是只计算返回值。

   ```ts
     function calc(a: number, b: number) {
       console.log('正在计算...');   // ← 往屏幕写了字，外部世界（屏幕）变了
       return a + b;
     }
   ```

   console.log 的「结果」不是返回值（它返回 undefined），它干的事全在外部：屏幕上多了一行字。这和 frame() 往 stdout.write 写本质一模一样——都是I/O。

   • 弹窗：改变了窗口系统的状态，用户得去点它
   • 改数据库：改变了磁盘上的持久数据，别的程序、别的请求都能看到

   它们都不满足「零外部影响」这条，所以统统是副作用。

   为什么"修改传入对象"要单独列一条

   因为其他几个（log/弹窗/数据库）是明显往外的，一眼能看出；而「改传入对象」是==隐蔽的往内==——参数本来就在函数手里，改它不需要任何"出口"，很容易被忽略。但它同样让函数不再可预测：你不知道调用一次会顺便把什么共享状态弄脏了。

   一句话：副作用的判据就一条——函数干的事，是否超出了"吃参数、吐返回值"这个边界。改传入对象、写屏幕、弹窗、改库，全是越界。





## 4.useEffect

   ```ts
 useEffect(() => {
   // ① 脏活：挂载后（或依赖变化后）执行一次
   stdout.on('resize', onResize);

   // ② 清理函数：组件卸载前执行（或下次重跑前）
   return () => {
     stdout.off('resize', onResize);
   };
 }, [stdout]);  // ③ 依赖数组：什么时候重跑
   ```

   执行时机：

   • 组件首次渲染完 → ① 执行（挂上监听）
   • [stdout] 里的值变了 → 先执行 ② 清理旧的，再执行 ① 挂新的
   • 组件卸载 → 只执行 ②（摘掉监听）



## 5.useMemo

useMemo 是 React 的「缓存 hook」——记住一次计算的结果，以后只要输入没变，就直接拿缓存，不重新算。

```ts
const value = useMemo(() => 计算过程(依赖), [依赖]);
```

- 第一个参数：一个函数，里面放「计算」
- 第二个参数：依赖数组，React 靠它判断“输入变没变”
- 返回值：计算结果

执行规则：

```text
首次渲染 → 执行函数，算出结果，存起来
之后每次渲染 → 检查依赖数组的每一项：
    ├─ 都没变 → 跳过计算，直接返回上次的结果（缓存命中）
    └─ 有变化 → 重新执行函数，更新缓存
```



一个直观例子

```ts
// ❌ 不用 useMemo：每次重渲染都重算，哪怕 items 没变
const sorted = [...items].sort();  // items 有 1000 项时就白算了

// ✅ 用 useMemo：items 没变就跳过
const sorted = useMemo(() => [...items].sort(), [items]);
```

类比：useMemo 像一个「带备忘录的函数」——第一次认真算，之后凭记忆回答，除非题目（依赖）变了。



三个记忆类 hook 的家族关系

| Hook        | 缓存的对象                              | 典型用途                          |
| ----------- | --------------------------------------- | --------------------------------- |
| useMemo     | 任意计算结果（数字、数组、对象、DOM……） | 昂贵的计算、给子组件的稳定 props  |
| useCallback | 函数（其实是 useMemo 包函数的特例）     | 传给子组件的回调，防止无谓重渲染  |
| useRef      | 一个可变的盒子，改它不触发重渲染        | 存定时器 id、DOM 引用、上一次的值 |



回到我们项目里的那一行

```ts
const shell = useMemo<ShellValue>(() => ({
  setMessage,
  setError
}), []);
```

拆解：

- 计算过程：`() => ({ setMessage, setError })`——新建一个对象
- 依赖：`[]`——空数组意味着“没有任何输入会变化”，所以只在首次渲染算一次，之后永远用同一个对象
- `<ShellValue>`：TypeScript 泛型，声明这个 useMemo 返回什么类型

为什么要包这一层？上一轮讲过：为了让 `shell` 的引用稳定。没有 useMemo 的话，每次 App 重渲染都会新建一个对象，ShellProvider 的 `value` 引用就变了，Context 机制会误以为“数据更新了”，平白拉着所有页面重渲染。



注意：useMemo 不是“必须品”

React 官方的态度是：useMemo 是性能优化手段，不是正确性保证。意思是：

- 不加 useMemo，代码功能上完全正确，只是可能多算几次
- 只有当你观察到性能问题（列表卡顿、无谓重渲染太多）时才需要加
- 滥用反而让代码难读——每个值都包一层 useMemo 是过度设计

所以昨天我说“留着也无妨”：现在这个空依赖的 useMemo 本质上就是“创建一次、终身复用”，和你问的“普通常量”效果相同，只是写法上借用了 useMemo 的缓存机制来达到引用稳定。
